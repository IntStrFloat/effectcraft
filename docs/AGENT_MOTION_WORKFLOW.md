# Работа агента с моушеном в EffectCraft

Читай этот файл в начале каждой сессии вместе с корневым `AGENTS.md` и `CLAUDE.md`.
Для задачи по анимации самостоятельно обеспечь работающий backend, создай редактируемую
сцену и проверь фактический рендер. Сборка при отсутствии бинарника и обратимые правки
входят в выполнение задачи.

## Запуск и сохранение работы

1. Используй уже подключённый MCP `effectcraft`. Прочитай `get_motion_workflow`, затем вызови `get_capabilities`, `get_state`
   и `get_project`: проверь backend, активный проект, композицию и несохранённые изменения.
   Не заменяй открытый проект демонстрацией или пустым проектом ради нового эффекта.
2. Если MCP недоступен текущему клиенту, найди CLI: путь из
   `codex mcp get effectcraft --json`, затем `effectcraft-cli` в `PATH`, затем
   `target/release/effectcraft-cli` этого checkout (`.exe` на Windows). Локальная установка
   также может находиться в каталоге пользователя `.codex/mcp/effectcraft/`.
3. Если бинарника нет, собери его один раз из корня репозитория:

   ```sh
   cargo build --release -p effectcraft-cli
   ```

   Нужен Rust **1.95** или новее. Проверь `--version`, затем фактический список инструментов
   `tools/list`: старая установленная версия может не содержать инструменты этого форка.
4. Для отдельной headless-сессии запускай `effectcraft-cli mcp --autosave`. Стандартный
   ввод/вывод — **UTF-8**, JSON-RPC строка на запрос: `initialize`, затем `tools/call`.
   Сервер ожидает запросы и не является обычной завершающейся shell-командой. Диагностику
   stderr держи отдельно от JSON stdout. Проверяй `isError` и содержимое каждого ответа.
5. Один процесс MCP хранит один проект. При работе через отдельные CLI-вызовы явно
   передавай `--project project.ecproj` и `--save` либо сохраняй через `--save-as`.
   Автосохранение headless не заменяет именованный проект: используй `save_project` после
   значимых этапов. Предупреждение о неудачном checkpoint требует сохранения в доступный путь.

Headless по умолчанию рендерит на CPU. `--gpu` подключает GPU backend; при недоступном
адаптере запуск завершится с причиной. Сверяй активный renderer через `get_project` и
возможности текущей сборки, а не по наличию видеокарты на компьютере.

GUI используй для визуальной работы в открытом проекте или по запросу пользователя.
Переиспользуй уже работающий экземпляр и его фактический control-порт. Если нужен новый,
запусти `effectcraft --control 0`, прочитай выведенный порт и подключись через
`effectcraft-cli mcp --bridge PORT`. `--autosave` нельзя сочетать с `--bridge`: checkpoint
desktop-проекта принадлежит приложению. Headless и bridge работают с разными проектами.

## Файлы, исходники и границы

Вызовы с путями должны использовать абсолютные пути. Для ограниченного сервера укажи
существующие каталоги через повторяемые `--automation-read-root DIR` и
`--automation-write-root DIR`. Write-root также разрешает чтение. При включённых корнях
скрипты и прямое управление UI ограничены; native engine-команды сохраняют проверку путей.
Подробности — [MCP conventions](mcp.md).

Сохраняй исходные медиа. Для эксперимента создавай новую композицию или вариант и храни
возвращённые id. Импортируй через `execute_command` → `file.import`, затем передавай
`source_item` для библиотечного изображения, видео или композиции. Не переименовывай
запрошенное медиа в фиктивный успешный источник и не заменяй отсутствующее видео картинкой
без явного описания результата.

EffectCraft — самостоятельный **alpha**-композитор. Он не открывает проекты `.aep`/`.aepx`,
не читает пресеты `.ffx` и не загружает Adobe SDK plug-ins `.aex`/`.plugin`. Собственные
WebAssembly effect plug-ins используют другой API. Схожее название встроенного эффекта
не доказывает пиксельную идентичность After Effects. Для работы со старыми AE-проектами,
их платными плагинами или точным клиентским соответствием эти ограничения существенны.

Перед выбором GPU прочитай [фактические проверки и ограничения](fork-validation.md).
На локальной RTX 4060/Vulkan воспроизводится расхождение CPU/GPU в мягких 3D-тенях;
установленный MCP по умолчанию использует проверенный CPU-режим.

## Цикл: запрос → редактируемая сцена → проверенный результат

1. Переведи запрос в назначение, характер, длительность, формат и точку события. Сначала
   пойми, что продолжает движение: объект, форма, экран, текст или камера. Общий смысл
   языка интерпретирует модель клиента; готовый рецепт не является встроенной LLM.
2. Получи `motion_catalog` и `plan_motion`. Прочитай допущения и реальные native-операции.
   Шесть стартовых рецептов создают **2D-сцены**. Камеры, пространственные слои, свет,
   трекинг и сложные маски достраиваются через общий реестр команд. Называй 2D/2.5D/
   объёмное 3D согласно устройству сцены, а не по впечатлению от перспективы.
3. Используй `create_motion_scene` для новой композиции. Храни фактические уникальные
   имена и id. Для существующей композиции сначала изучи `get_comp`, `get_layer` и
   `get_property`; выполняй адресные изменения через `animate_layer`, `set_property`
   и `add_keyframe`, сохраняя исходник и намеренную анимацию пользователя.
4. Точные имена свойств бери из дерева слоя, эффекты — из `list_effects`, шрифты — из
   `list_fonts`, собственные WASM-плагины — из `list_plugins`. Цепочку применяй через
   `apply_effect_chain`: `append` добавляет эффекты, `replace` заменяет прежние эффекты
   целевого слоя вместе с их параметрами/ключами. Не выдумывай параметры и установленные
   плагины. Все остальные маски,
   формы, камеры, свет, трекинг и рендер доступны через `list_commands`,
   `describe_command`, `execute_command` и `batch`.
5. Ключи всегда ставь с явной временной базой. Низкоуровневые `set_property`/
   `add_keyframe` по умолчанию используют **layer time**, а кадры рендера — **comp time**.
   Для совпадения с таймлайном передавай `timeBase: "comp"`; учитывай start, stretch,
   reverse и привязку к реальным кадрам композиции.
6. Проверь `analyze_scene`, затем `render_storyboard` на нескольких фазах: перед входом,
   вход, удержание, выход, последний допустимый кадр. Для детализации используй
   `render_frame`. Изучи фактические изображения: разницу фаз, читаемость, границы,
   alpha, маски и перекрытия. Одного красивого статического кадра недостаточно.
7. Уточни кривые и параметры. Анимация должна иметь понятный вход, читаемое удержание
   и завершение; на шве сохраняй выбранную опору и скорость. Учитывай хвост SFX и
   смену аудиоплана. Не объявляй проверенным звук, который не прослушан.
8. Сохрани `.ecproj` через `save_project`. Экспортируй через native Render Queue:
   `renderQueue.add` → `renderQueue.render`. Для MCP progress/cancel используй прямой
   blocking `execute_command` рендера с progress token; проверяй итог, путь, кадры,
   длительность, формат и alpha, а не только факт добавления задания в очередь.
9. Повторно открой сохранённый проект в отдельной проверочной сессии, проверь источники
   через `footage.check` и сравни контрольные кадры. Не заменяй этим открытый проект
   пользователя с несохранёнными правками.

`batch` группирует изменения в одну отмену и по умолчанию откатывает неудачный шаг.
`command_batch` выполняет шаги по отдельности. `run_script` может оставить изменения,
сделанные до исключения; его поведение не следует считать транзакционным.

## Перед завершением

Укажи созданные композиции, пути проекта и экспорта, реально проверенные кадры/фазы и
оставшиеся ограничения. `analyze_scene` — проверка структуры, не художественный вердикт.
Одинаковые sampled frames не доказывают отсутствие анимации на всей временной линии.
Ограниченный storyboard не сертифицирует весь длинный рендер.

Публикуемые ассеты должны отвечать `AGENTS.md`: открытая лицензия или оригинальная работа,
sidecar `.attribution` и запись в `ATTRIBUTION.md`. Локальные закрытые исходники, референсы
Adobe, чужие пресеты и аудиобиблиотеки не добавляй в публичный форк.

Подробности: [motion MCP](motion-mcp.md), [native agent tools](agents.md),
[control protocol](control-protocol.md), [known gaps](gaps.md), [plug-in API](plugins.md).
